## 結論

## 所見

### A1 (High) editor ≠ approver の判定が機能していない
- 場所: `crates/ipemu-server/src/manifests.rs` `approve()`: `row.updated_by == actor.id` で比較しているが、`updated_by` / `created_by` には**ユーザ名** (`p.name`) を保存しており (`api/admin.rs` `insert_revision` / `update_revision`)、`actor.id` は UUID。等しくなることがないため、編集した本人がそのまま承認できる。
- 影響: 設計 (06「編集と承認は別ロール」) の要である役割分離が無効。承認の意味がなくなる。
- 修正: 編集者・承認者は **ユーザ id** で保存・比較する (表示用に名前も持つ)。「同一ユーザが編集 → 承認」が 403 になる結合テストを追加。

### A2 (High) launch トークンが管理操作に使え、「新鮮なログイン」として扱われる
- 場所: `crates/ipemu-server/src/auth.rs` `authenticate()`: チケット交換で得る `lt_` トークンは `kind = "launch"` だが、以後の認可は `Principal.roles` だけで決まり、`AdminAuth` も `require_fresh_login` もトークン種別を見ない。`issued_at` は交換時刻なので常に「1 時間以内」。
- 影響: チケットは `ipemu://` URL に載って外部ブラウザ・OS・ログを経由する。承認者のチケットが漏れると、1 時間は承認・公開・ユーザ操作まで可能。D36 の緩和策 (1 時間以内のセッション要求) が逆効果になる経路。
- 修正: `CredentialKind::Ticket` の主体は**配信 API (catalog / manifests / artifacts / telemetry / hello) のみ**に制限し、`UserAuth` (チケット発行) と `AdminAuth` では拒否。`require_fresh_login` は `Session` 資格情報にのみ成立。テスト: launch トークンで承認 → 403、カタログ取得 → 200。

### A3 (Medium) エンジンの静的検証 (V12 など) が同意・実体化の後に走る
- 場所: `crates/ipemu-engine/src/session.rs` `Session::load`: 第 1 パス → V7 → 同意 → 実体化 (`init` まで実行) → `validate()` (V2〜V12)。`approval.capabilitiesHash` の不一致 (V12) や V2 / V11 の誤りがあっても、同意を求め、実グラントで部品を実体化して `init` を走らせてから失敗する。
- 影響: 承認後に宣言が書き換わった manifest (署名のないローカル経路、またはサーバ側の不整合) でも、同意さえ取れば `init` 中の I/O が通る。設計 (04 V12、「宣言のない I/O は起きない」) の意図から外れる。署名付き配信経路では `ipemu-sign::verify_manifest` が先に V12 相当を行うため実害は限定的。
- 修正: `validate` を「記述を要しない静的検査 (V1, V2, V3 の builtin 名, V7 の self_check, V10, V11, V12)」と「記述を要する検査 (V3〜V9)」に分け、静的検査を**同意の前**に実行する。テスト: capabilitiesHash 不一致の manifest で同意要求が出ず実体化もされないこと。

### A4 (Medium) キャッシュのパスに未検証の manifest id が入る
- 場所: `crates/ipemu-engine/src/cache.rs` `manifest_dir()` は `manifest_id` をそのまま `join` する。`bootstrap.rs` は CLI (`--launch`) や `ipemu://` の `manifest` パラメータをそのまま渡す。`server_key()` はサニタイズしているが id はしていない。
- 影響: `../../x` のような id でキャッシュ外にファイルを書ける (内容はサーバ応答)。シェルの信頼 origin 判定が一次防御だが、CLI 経路には無い。
- 修正: manifest id をスキーマの `^[a-z0-9][a-z0-9-]{2,63}$` で検証してから使う (`bootstrap` の入口と `Cache` の両方)。revision は数値のみ。テスト追加。

### A5 (Medium) 部品アップロードの本文上限が 2MB のまま
- 場所: `crates/ipemu-server/src/lib.rs` に `DefaultBodyLimit` の設定がなく、axum の既定 (2MB) が `Multipart` に効く。`upload_artifact` の `max_artifact_bytes` (32MB) 判定に到達しない。
- 影響: UI バンドル (tar.gz、数 MB) やデバッグ情報付きの wasm が 413 で登録できない。
- 修正: アップロード経路だけ `DefaultBodyLimit::max(max_artifact_bytes + 余裕)` を設定し、他は既定のまま。3MB の登録が通るテスト。

### A6 (Low) 同意ファイルの鍵を全体小文字化している
- 場所: `crates/ipemu-engine/src/consent.rs` `FileConsent::from_file` / `lookup`。capability 文字列には `fs:rw:<path>` のパスが含まれ、パスは大文字小文字を区別する。
- 修正: 小文字化は sha256 部分に限る (ホスト名は宣言時点で小文字化済み)。

### A7 (Low, 記録) 名前解決がスケジューラスレッドをブロックする
- 場所: `crates/ipemu-wasm/src/wasi.rs` `NetAllow::resolve` が `to_socket_addrs` を同期で呼ぶ。DNS の遅延がそのまま仮想時間の進行を止める。epoch interruption はホスト関数内では効かない。
- 対応: 設計上は単一スレッド前提で許容。Docs 07 に制約として記載し、M6 でタイムアウト付きの解決 (別スレッド + 期限) を検討。

### A8 (Low) ログイン抑止がユーザ名だけを鍵にしている
- 場所: `auth.rs` `LoginThrottle`。第三者が 5 回失敗させるだけで正規ユーザを 30 秒ロックできる。
- 修正: 鍵を (ユーザ名, 送信元 IP) にし、ユーザ名単独は閾値を高く (例 50 回) する。

### A9 (Low) telemetry の `event` / `detail` に長さの上限がない
- 場所: `api/v1.rs` `telemetry`。Json extractor の 2MB が唯一の上限。
- 修正: `event` は 64 文字、`detail` は 16KB までで 413 / 400 を返す。

### A10 (Low) カタログが構成ごとに revision を引く (N+1)
- 場所: `api/v1.rs` `catalog`。構成が増えると遅くなる。
- 修正: revision を 1 クエリで取得して集約する。

## 確認できたこと (問題なし)
- capability: 宣言のない import は link されず実体化で失敗する。`validate` / `inspect` / サーバの describe は deny-all 形 (レビューで修正済み)。fs の閉じ込めは文字列規則と canonical パスの二重確認。名前解決は許可ホスト限定で、解決した IP はそのエントリのポートにだけ接続可。
- 同意: 鍵は `sha256(artifact):capability`。拒否・未同意が 1 件でもあれば部分起動しない。ワイルドカードは開発モード限定。
- 署名: JCS (RFC 8785 付録サンプルで検証) と capabilitiesHash は `ipemu-core` の単一実装をサーバ・クライアントが共有。`verify_manifest` は署名の後に capabilitiesHash も照合。未公開 revision (署名なし) は `allow_unsigned` なしでは拒否される。
- 配信 API: トークンはハッシュ保存、チケットは原子的 UPDATE で単回、`by-hash` は 64 桁 hex を検証、ETag / immutable、公開範囲外は 404。
- 管理 API: 破壊的操作は承認ロール + 新鮮なログイン、CSP と nosniff を全応答に付与。
- エンジン: 決定性 (NaN 正規化、壁時計なし、シード付き PRNG)、4 形態でプラント軌道がビット一致、FAULT 経路、ゴールデントレース。
- 部品 / FW: `wasm32-unknown-unknown` + `wasm-tools` で WASI 非依存。C 版は freestanding + Rust libm。HAL の vtable は `ip_hal.h` と Rust 側でレイアウト一致。
- 文書: Docs/08 の決定番号 D1〜D40 に重複なし。各 Docs に実装節あり。
